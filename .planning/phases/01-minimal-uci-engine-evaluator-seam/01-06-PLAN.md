<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Manual GUI validation of a full legal game (TOOL-01)</name>
  <action>No code changes in this task — present the verification steps below to the human and wait for explicit confirmation that a full game completed cleanly in Cute Chess or Arena.</action>
  <what-built>
    A complete UCI engine (`<repo>/.venv/bin/python -m ance`) that
    completes the `uci`/`isready` handshake, accepts `position`/`go`/
    `stop`/`quit`, plays legal moves chosen by a fixed-depth negamax
    through the full Simplified-Evaluation-based `HandcraftedEval`,
    rejects malformed input without crashing, and preempts a running
    search cleanly (stop -> join -> clear, with a search-generation gate
    against stale output, round-2 hardening) when a new `go`/`position`/
    `ucinewgame` arrives mid-search — all verified automatically by the
    pytest suites in Plans 01-01 through 01-05.
  </what-built>
  <how-to-verify>
    1. Install Cute Chess (prebuilt macOS binary from
       `https://github.com/cutechess/cutechess/releases`) or Arena, if
       not already installed.
    2. Register a new UCI engine pointing at
       `<repo>/.venv/bin/python` with the argument `-m ance` (or the
       equivalent "command + arguments" fields your GUI exposes).
    3. Start a new game with ANCE on one or both sides (ANCE vs. itself,
       or ANCE vs. a built-in weak opponent), at any time control.
    4. Confirm: (a) the engine shows as "ready"/loaded with no error
       dialog during the handshake; (b) the engine responds with a legal
       move every turn without the GUI ever reporting "no response",
       "timeout", or disqualifying the engine; (c) the game reaches a
       natural result (checkmate, stalemate, draw, or resignation-
       equivalent) rather than hanging or crashing mid-game.
    5. (Round-2 MEDIUM finding — GUI expectation for preemption.) At some
       point mid-game, if the GUI exposes a way to interrupt/change the
       position while ANCE is still thinking (e.g. taking back a move or
       loading a new position while ANCE's clock is running), trigger it
       and confirm the GUI accepts ANCE emitting a `bestmove` for the
       position it was preempted from, followed by a fresh `go` on the
       updated position — some GUIs instead expect a silent cancellation
       with no `bestmove` for the stale position, which is worth
       surfacing here even though it is UCI-legal behavior per D-13's
       preemption policy. If the GUI has no such interactive control,
       this step may be skipped and noted as skipped in the resume
       signal.
    6. (Round-2 MEDIUM finding — clock-based time controls, not just
       `movetime`.) Start a second game using the GUI's normal clock time
       control (so the GUI sends `go wtime <ms> btime <ms> winc <ms> binc <ms>`
       rather than a fixed `movetime`) — e.g. a 5-minute or 3+2 game.
       Confirm ANCE still responds with legal moves every turn and the
       game completes without the GUI reporting a timeout, even though
       Phase 1 only parses these clock parameters and does not act on
       them (real clock budgeting is Phase 3, UCI-08) — this exercises a
       path that Plan 01-03 covers automatically for parse-safety only,
       not for a live GUI clock.
  </how-to-verify>
  <resume-signal>Type "approved" once a full game completes cleanly in the GUI (including the clock-time-control game from step 6, and step 5's preemption check if the GUI supports it), or describe exactly what went wrong (e.g. "hung after move 12", "GUI disqualified on time", "handshake never completed", "GUI rejected the bestmove for the preempted position").</resume-signal>
</task>
